# FilmBuddy state

FilmBuddy is a single-user PWA. All app data lives in one in-memory `AppState` object, persisted to `localStorage`, and optionally mirrored to S3 as a JSON snapshot.

## Shape

`AppState` (see `packages/app/src/state/types.ts`) is a flat collection of normalized arrays plus a small amount of backup metadata:

```ts
type AppState = {
  cameras: Camera[];
  rolls: Roll[];
  shots: Shot[];
  stocks: Stock[];
  lenses: Lens[];
  filters: Filter[];
  backupKey: string;
  lastBackupAt: number | null;
};
```

Records reference each other by string id. Nothing is nested.

### Entities

- **Camera** — `{ id, name, currentRollId? }`. `currentRollId` points at the roll currently loaded in the camera, or `null` when empty.
- **Roll** — `{ id, cameraId, stockId, iso, length, startedAt, completedAt?, shotCount, digital? }`. A roll belongs to one camera. `completedAt` is `null` until the roll finishes. `digital: true` marks the synthetic "roll" used for digital cameras (see `addCamera` with `startDigitalRoll`); digital rolls never auto-complete and are excluded from the completed-rolls list.
- **Shot** — `{ id, rollId, frame, aperture?, shutter?, lensId?, filterId?, note?, ts }`. Frames are 1-indexed within a roll. A shot is created either by logging aperture/shutter/note (`logShot`) or by setting the active lens/filter (`setLensFilter`). When a lens/filter change lands on a frame that doesn't yet have a shot, a placeholder shot is inserted; logging on that same frame later fills in the exposure fields.
- **Stock** — `{ id, name, boxSpeed }`. Film stocks are created on demand the first time a user types a new stock name when loading a roll.
- **Lens / Filter** — `{ id, name }`. Same lazy-creation pattern as stocks, keyed case-insensitively by name (`ensureByName` in `mutators.ts`).

### Backup metadata

- **`backupKey`** — a stable per-install identifier (`fb-xxxx-xxxx-xxxx`, generated by `generateBackupKey` in `id.ts`). This is the key under which the snapshot lives in S3 and the value the user enters on another device to restore. It is *not* overwritten when a snapshot is restored from S3 — see `restoreFromSnapshot` in `mutators.ts`, which preserves the local `backupKey`.
- **`lastBackupAt`** — millisecond epoch timestamp of the last successful upload, or `null`. Selectors derive "backup is stale" from this (`BACKUP_STALE_DAYS = 15`).

### IDs

All ids are generated by `uid(prefix)` in `state/id.ts` using `crypto.getRandomValues` — e.g. `cam-a3f9kp`, `roll-...`, `shot-...`, `stock-...`, `lens-...`, `filter-...`. IDs are local to the install; two devices will have disjoint id spaces unless one restores from the other.

## Where state is stored

### In memory

The state lives in a single React context provided by `AppStateProvider` in `packages/app/src/state/store.tsx`. Components read via `useAppState()`, which returns `{ state, mutators }`. Mutators are pure functions in `state/mutators.ts` that take the current state and return the next state; the provider wires them to `setState`.

### `localStorage`

`loadState` / `saveState` in `state/persistence.ts` serialize the entire `AppState` as JSON under the key **`filmbuddy.state.v2`**. Every state change triggers a save via a `useEffect` in the provider. On first load, if no entry exists (or parsing fails), `emptyState()` is written and returned — this is also where a fresh `backupKey` gets minted.

Loading uses `{ ...emptyState(), ...parsed }`, so new top-level fields added to `AppState` will populate with defaults rather than crash older stored blobs. Field-level migrations would need explicit handling.

### S3 snapshot

`packages/app/src/backup/client.ts` uploads and downloads the full `AppState` as a single JSON object:

1. The client POSTs `{ key, action: 'put' | 'get' }` to the backup API (URL from `VITE_BACKUP_API`). The API vends short-lived STS credentials scoped to one object.
2. `uploadSnapshot` PUTs `JSON.stringify(state)` directly. `downloadSnapshot` GETs the object and validates it through `appStateSchema` (Zod, in `backup/schema.ts`) before returning it.
3. On successful upload the app calls `markBackedUp` to update `lastBackupAt`.
4. Restoring calls `restoreFromSnapshot`, which replaces everything *except* the local `backupKey`.

The Zod schema mirrors the TS types and enforces the `backupKey` pattern on inbound snapshots. It is the only place in the client where stored data is validated; localStorage reads are trusted.

## Selectors and derived data

Everything view-side is derived with the helpers in `state/selectors.ts`:

- `currentRoll(state, cameraId)` — roll pointed at by `camera.currentRollId`.
- `shotsForRoll(state, rollId)` — sorted by frame ascending.
- `completedRollsForCamera(state, cameraId)` — excludes digital and in-progress rolls.
- `effectiveLensAt` / `effectiveFilterAt` — carry-forward lookup: walks shots backward from a given frame and returns the most recent non-null `lensId` / `filterId`. `currentLensId` / `currentFilterId` are the same thing at the tail of the current roll.
- `isBackupStale`, `relTime`, `daysSince` — time formatters driven off `lastBackupAt`.
- `suggestStrings` — dedup'd auto-complete sources pulled from prior `stocks`, `lenses`, `filters`, camera names, apertures, shutters.

Because lens/filter are stored per-shot but rendered as "currently mounted", `setLensFilter` writes a shot at the current (or chosen) frame rather than mutating a roll-level field. This keeps history accurate even when a lens or filter is swapped mid-roll.

## Invariants worth knowing

- A camera has at most one active roll at a time. `loadRoll` auto-completes the prior non-digital roll on the same camera before attaching the new one.
- Deleting a camera cascades to its rolls and their shots (`deleteCamera`). Deleting a roll cascades to its shots and clears `currentRollId` if it pointed at the deleted roll.
- `shotCount` on a roll tracks the highest frame that has been touched — it grows monotonically when logging or setting lens/filter on higher frames.
- Stocks, lenses, and filters are append-only in practice: nothing deletes them. Duplicate entry is prevented by case-insensitive name match in `ensureByName`.
